# Equipment observation, process history and energy

[中文](README.zh-CN.md) · [Current machine contract v2](../../../contracts/published/http-api/equipment-observation-v2/README.md) · [r10 specification](../../../plans/ARCH-OBS-001-configuration-driven-equipment-monitoring/spec.md#r10-source-independent-energy) · [User guide](../../../docs/equipment-status-process-monitoring.md#r10-guide)

The manifest registers machine ingestion, human reads and administrator configuration. In r10, SMA, a third party or another authorized program use the same source-independent v2 contract; PLC facts and task-point evidence are not prerequisites. This describes the backend contract, not implementation or operation of a particular SMA or PLC. `sourceRefs` is optional sender-declared metadata, not verified provenance. The published [v1 contract](../../../contracts/published/http-api/equipment-observation-v1/README.md) is historical. The post-retirement source rejects v1 events after identity and scope checks and never replays v1 receipts. Equipment and process requests use the configured database connection. They no longer preflight a global migration revision or target metadata from the private profile. The profile continues to govern business access.

`equipment_main` keeps the latest complete multi-group snapshot per equipment and task; `monitor_main` appends configured historical measurements for a task; `energy_consumption_main` appends independent meter samples without a task. Events supply their original `observedAt`; the server preserves the event time and converts offset-bearing timestamps to the project time zone. Persistent receipts and independent target/event retries provide idempotency as described in the v2 contract. A latest request can clear omitted groups and therefore requires authorization for its full replacement scope.

Equipment and process observations share the `observation_metric_*` configuration tables and write receipts to `observation_ingest_receipts`. Meter samples use `energy_ingest_receipts` independently. The migration preserves existing IDs and retry results.

The receipt migration supports inherited schema and table collations `utf8mb4_0900_ai_ci` and `utf8mb4_unicode_ci`. Explicit binary identifier columns retain `utf8mb4_bin`. It checks the MySQL 8.4 predecessor's enforced CHECK expressions and each affected character column before any migration DDL.

Administrators configure regions, stable metric keys, display names, units, cards, curves and history retention separately; the Web uses those settings, not slot numbers or translated titles, to interpret and display values. The external private profile is default-off and supplies machine credential digests and scopes for equipment, targets, groups, metrics and meters. Machine discovery and writes follow those grants; human reads and management use separate permissions and device/meter scope checks. Alembic migrates the schema explicitly; startup and module registration do not create or seed tables. Existing acquisition facts and APIs retain their own contracts and permissions.

The standalone write-source registration and anonymous read/write contract are documented separately. [Registered source contract](../../../contracts/published/http-api/observation-write-sources-v1/README.md)

Energy runtime verifies the configured MySQL server and schema identity and no longer depends on the global migration revision or the equipment source table. Administrators register independent energy sources. [Energy registered batch ingest](../../../contracts/published/http-api/energy-registered-ingest-v1/README.md) documents the token-free multi-meter POST, one receipt and atomic sample writes.

The energy integration surface also exposes token-free GETs for the latest sample per meter and group and for paginated history. The older POST on the history path retains its machine Bearer authentication. Web reads and management continue to use user Bearer authentication. [Public energy reads](../../../contracts/published/http-api/energy-public-reads-v1/README.md)

Energy administrators can add or update meter names and read roles. Apply the guarded `9e0c5d41b7a2` migration before adopting this service revision. Supply `ENERGY_METER_EXPECTED_SCHEMA` and `ENERGY_METER_EXPECTED_SERVER_UUID` for the independently approved target. Unedited profile meters remain available under their original scopes. [Energy meter management](../../../contracts/published/http-api/energy-meters-v1/README.md)

Energy curve groups save an ordered list of numeric metrics for one meter and sampling group. The existing meter scopes govern management and statistics reads. Apply `af6d8b2c4e90` after `9e0c5d41b7a2` on an independently approved target and supply `ENERGY_CURVE_EXPECTED_SCHEMA` and `ENERGY_CURVE_EXPECTED_SERVER_UUID`. The migration adds one configuration table. Keep it when rolling back application code. [Energy curve groups contract](../../../contracts/published/http-api/energy-curve-groups-v1/README.md)
