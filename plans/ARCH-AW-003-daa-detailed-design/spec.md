## 4. 编号需求

### R1. 文档效力与唯一依据

正文明确是目标设计与接口语义草案，不代表实现、冻结协议、数据库迁移、现场操作或各端任务批准。链接 AW 白皮书、运行设计和本 spec；根任务 bundle 只保存范围、实施证据与验证事实。

只对 `docs/AIIS_AW_Runtime_Design.md` 做最小指向/效力补充：DAA 的全样本、跨 DB 采集组、双库和补传选择由新正文细化；旧文的 latest/samples 待决及通用降级选项不继续作为本次 DAA 目标的默认选择。保留原文历史与 AW 总体职责，不重写白皮书、ROADMAP 或 ARCH-AW-002 bundle，不将新设计提升为现行可执行合同。

### R2. 多 PLC 与连接生命周期

一个 DAA 实例支持多个 PLC；各 PLC 具有稳定标识、独立连接、采集任务与故障状态，IP 是可修改属性。正常采集复用长连接，同一连接的读操作串行；不同 PLC 可独立执行，一个 PLC 故障不阻塞其他 PLC。

说明连接、采集运行意图与容量暂停分别管理：意外断线退避重连，人工断开停止自动重连，修改连接参数或显式退出有序关闭。采集组停用不自动等同主动断开 PLC。窗口关闭是否退出、后台托管、开机启动和支持平台列为独立待决项，不凭 Tauri 名称承诺。

### R3. 配置、完整结构与采集组

UI 编辑 PLC/点位/采集组/上传策略后，由本机配置服务保存 SQLite；YAML 不再成为目标业务配置权威。导入 `.db`/`.udt` 前选择所属 PLC、DB 号，保存完整 DB/UDT、来源和引用；区分 PLC 文本源 `.db` 与 SQLite 文件。

整 DB 偏移推算须手动触发，基于完整结构，受标准非优化 DB 和明确支持矩阵限制；缺定义或不支持时拒绝猜测，先预览再写草稿。支持人工修正并保留来源，重新推算不能静默覆盖人工值；结构/类型变化标记受影响地址待复核。输入可解析、读取成功均不证明与 TIA 实际地址一致。

一个组属于一个 PLC，可选择该 PLC 多个 DB 的部分点位；同一点最多属于一个组。PLC、组、点位均启用且点位已分组才采集；关闭点位不删除完整结构和历史身份，未分组明确显示未采集。点位移组保留稳定身份。提供按整个 DB 建组的快捷概念，不强制按 DB 划分。

### R4. 独立采集周期、实际读取与样本语义

组独立设置采集周期；上报周期另设。运行时按 DB/连续地址范围组织实际读取，在本地解码启用点；整 DB、逐点、合并区间作为读取权衡说明，不冻结驱动算法、PDU 限额或性能数值。

同组不重入，不无限堆积错过的调度；超期记录实际耗时、延迟和错过次数，不补造过去样本。多 DB/分段读取保留实际时间、质量与成员结果，不能称为同一瞬间的一致快照。成功实际采到的每份样本先持久保存，不合并丢掉中间值；失败不拿旧值或 0 冒充新成功，轮询也不承诺捕获采样间短脉冲。

### R5. 双库、版本解释与恢复不变量

每个 DAA 实例各自拥有 `config.sqlite` 与 `runtime.sqlite`，实例内全部 PLC 共用这一对，其他实例不共用打开的可写库。

- 配置库保存 PLC/完整结构/点位/组/端点/策略及 draft、active、previous；凭据只描述引用与存储责任，具体安全方案待定。
- 采样库保存不可变样本、上传批次及成员、样本级确认、重试/需处理记录、解释历史所需的不可变配置摘要。摘要不是第二套可编辑配置。
- 样本固定配置 revision；配置回退不删除样本或运行记录，不倒退身份、序号、确认和游标。配置备份恢复不能倒退采样库进度；采样库重建涉及新的来源代次。
- 明确配置持久提交、采样库解释摘要、内存激活与首次使用新 revision 的次序和崩溃恢复目标；不得假设两个 WAL 数据库有整体原子事务，不能旧内存采集却报告新 revision 已生效。

单写协调、短事务、读取提交后再上传、HTTP 位于事务外作为可靠性要求。WAL + `synchronous=FULL` 为待吞吐/恢复验证的提交基线建议，具体库/版本/参数不在本轮定案；后续选型须核验官方已知限制和已公布修复，不能只因版本号较新宣称安全。

### R6. 样本确认与冻结批次

样本事实只保存一份；样本级 ack 与投递批次状态分开。样本可先由优先批次确认，之后又出现在此前冻结的历史批次重试中；保持同一 `sampleId`，ack 单调不倒退，不仅按所属单一批次推导可清理性。

形成批次前限定数量与字节；发送前持久化批次身份、固定成员和内容，HTTP 在事务外。可靠持久化回执后才确认对应样本，断网/超时/重启保持原身份重传。说明待上传、上传中、等待重试、已确认、需处理的展示语义及其归属，不将整批/逐样本确认混用。

可重试错误退避且限流；鉴权/合同拒绝明确阻塞或隔离，不进行无效无限重试、不自动丢弃。整批事务确认可列为首版建议；后端未确认部分成功策略前，不承诺具体回执 schema。清理已确认样本时需处理冻结批次仍引用它的生命周期，不能提前删掉重试所需内容或让元数据无限增长。

### R7. 天数、容量与暂停恢复

保留期建议从本地成功保存时间计，采集时间独立保留。只自动清理已确认样本：正常按天数，容量紧张可提前清理最旧已确认数据；未确认及需处理样本超期仍保护。

存储额度覆盖采样库、WAL 等附属占用，同时设置系统磁盘最低余量，预留确认/清理/checkpoint 空间。区分有效数据、可复用页与实际文件大小；DELETE 不等于立即缩文件，按批清理、控制长读事务、在低负载维护回收，不把频繁整库 VACUUM 当热路径。

保护数据已占满且无法安全继续写入时，暂停本实例新增采样，上传/诊断继续，留下停采原因与时间缺口。低水位恢复只恢复原本希望运行的 PLC/组，不启动人工停止对象；无限期断网、有限磁盘、持续全量采集不能同时保证。全样本保证从成功本地事务提交开始，落盘前崩溃/失败、停采和磁盘损坏的边界诚实说明。

### R8. 最新优先与历史公平补传

恢复时先上传各组最近实际采到的原样本，保留原身份、采集时间和质量；不能用重新取时间的快照替代，不能将多组拼成虚构同步帧。之后按预算交替新样本与历史补传，各 PLC/组有公平机会，历史不被持续新数据饿死。

上传周期与批次数量/字节/并发/速率限额分别说明；补传吞吐需高于新增速率才可能消减积压，但不承诺固定恢复时长。最新优先只改变发送顺序，不改变 raw 样本集合或可靠回执要求。

### R9. 稳定身份、来源顺序与完整接收边界

给出语义信息表而非正式 JSON schema：稳定样本/批次身份、DAA/PLC/组/点位身份、配置 revision、值/类型/质量、采集/本地保存时间、`sourceGeneration` 与 `sourceSeq`、确认范围和错误可重试性。

同一来源代次内，PLC 内保持持久递增顺序，跨组可比较；正常重启不清零，序号与对应事实原子保存。不同 PLC 的裸序号不比较，配置回退不重置。新库/实例交接的新代次及唯一有效来源由 Backend 受控确认，不以 UUID 或本机时钟排序代次。

必须说明 sourceSeq 分配粒度与 PLC 完整事实单位，以及跨 DB 一轮的成员/质量完整性；若分片，说明片段身份和完成条件。组/点位过滤后的自然跳号不是丢失，不能把组内裸序号连续性用作 PLC 接收完整性证明。具体字段与 manifest/分片 schema 留给后端合同确认。

完整接收边界是已可靠收到的连续事实前缀，不能用最大见过序号代替。包含“1000 已完整，1005 优先到达，1001–1004 补齐，再重复 1005”的推演；边界分别为 1000、1005，重复不新增事实。连续接收也不证明采集无时间缺口；记录读取失败、停采与永久不可补齐，并明确缺口接受/跳过须有策略与结果标记。

### R10. Backend 接收与读取配合合同

DAA 使用一个公开接收 API；Backend 拥有 raw/latest 内部存储与 schema，不让 DAA 直库或依赖内部表名。

- raw 按稳定样本身份去重追加；同身份同内容重复仍可确认，同身份不同内容拒绝冲突。
- latest 按点位/来源有效性和更高源顺序原子条件推进，补传旧数据不能覆盖新值，并发请求也不能倒退。具体代次交接、质量/配置变更及停用点位的展示策略由后端确认。
- 回执只在约定可靠持久化完成后发出，明确 raw/latest/接收记录的事务与失败边界；仅入队与可靠保存不混称成功。
- 对 SMA 提供保证并发提交不漏读的增量游标与完整性信息；不能假设 raw 自增 ID 或最大 sourceSeq 天然可作安全接收游标。
- raw、去重记录、增量 feed 保留期覆盖允许补传窗口与 SMA 滞后；超期明确缺口/重同步，不能静默漏读或把重放当新事实。

只写信息需求、责任、拒绝/确认语义及共同验证场景；API 路径/版本/鉴权、响应包装、DDL、索引、正式字段/单位、部分接收与游标实现由后端专属会话独立立项，不在本轮修改 `contracts/` 或 Backend 文件。

### R11. SMA 去重、乱序与持久进度配合合同

区分四类处理：实时 latest 可跳到新状态，恢复首帧重建基线而非冒充新上升沿；逐样本无状态处理按身份去重可乱序；有状态处理按源序等完整缺口后推进；窗口按原采集时间，暂定/修正采用稳定窗口身份。

持久接收游标与每个流程的处理进度分开，最大见过 sourceSeq 不能替代接收游标。输入落库与接收游标原子；处理去重检查、流程状态、处理 checkpoint 和输出 outbox 原子；对外 HTTP 位于事务外。

处理身份至少含流程 ID/版本/样本身份，输出另区分节点/目标；同流程版本重启重放不得重复产生已记录输出。对方 API 需支持幂等键或结果核实，才可防止回执丢失造成重复外部效果；不虚称端到端恰好一次。流程改版后的历史重算必须显式区分正常补传，不默认为全部重跑。

列明 SMA 等缺口、迟到修正、部分目标失败、游标过期和来源代次切换的需求与责任，具体 Flow Core、SMA schema/节点/运行时实现留给 SMA 专属会话。

### R12. 诊断、待决项与跨会话 handoff

信息设计至少覆盖 PLC 连接/期望状态、实际采集间隔/耗时、配置 revision、值的时间/质量、未确认数量/容量/最旧时间、最近确认、重试/拒绝、磁盘余量、容量暂停、补传及 SMA 完整性边界。日志只定义必要状态变化/关联身份和脱敏责任，不新增日志实现或将每轮明细定为默认噪声。

正文给出 DAA/Backend/SMA 三方责任和实施前确认清单、后续候选窄阶段及验证入口。本次仅形成供 Human Owner 转交的材料，不消息其他会话，不把联动需求记成对方已承诺。

## 7. 正文必须包含的故障与验证场景矩阵

这些是设计审阅和未来各 owning task 的验收输入，本轮不执行运行实验。每行至少写预期行为、持久/确认边界、负责方和实施时所需证据：

| 场景 | 设计必须能回答的问题 |
| --- | --- |
| 一个 PLC 断线，其他 PLC 正常 | 独立采集/重连与人工停连状态如何保留 |
| 两组周期不同、跨 DB、读取超期 | 非重入、实际时间/质量和错过调度如何呈现 |
| DB/UDT 缺失、推算不支持或人工改址 | 如何拒绝猜测、保留完整结构并避免误应用 |
| 配置磁盘提交与内存激活之间崩溃 | 如何恢复一致版本，样本如何继续解释 |
| 读到值但本地提交失败/突然退出 | 哪些结果未受持久保证，如何显示失败/缺口 |
| 后端已保存而回执丢失 | 相同身份重试、raw 不重增、ack 不提前 |
| 最新样本已确认，旧冻结批次再次携带它 | 样本级 ack、批次内容、重试与清理怎样保持一致 |
| 1005 先到，再补 1001–1004，再重复 1005 | latest 不倒退、连续完整边界正确、raw 去重 |
| PLC 内跨组过滤或跨 DB 一轮分片 | 自然跳号与真实缺口如何区分，何时认定完整 |
| 重启、采样库重建或采集实例交接 | 哪些身份连续，何时必须 Backend 确认新代次 |
| 鉴权失败、同 ID 异内容、不可重试拒绝 | 数据如何保护、隔离和定位，合法数据如何继续 |
| 长时间断网与持续新样本 | 最新/历史公平预算、容量上涨及恢复吞吐边界 |
| 已确认超期、未确认超期、保护数据满额 | 清理、暂停、预留空间、低水位与人工停组规则 |
| 大 WAL、长时间历史读事务、磁盘余量不足 | 实际占用与可复用页、checkpoint/回收如何协调 |
| SMA 先收到新样本，后收到历史 | 实时重同步/无状态/有状态/窗口分别如何处理 |
| SMA 在输入或输出确认边界崩溃 | 接收/处理游标及 outbox 事务如何避免漏读/重复效果 |
| Backend 并发提交、feed 过期或 SMA 长期滞后 | 安全增量读取、保留对齐及明确缺口/重同步 |
| 第三方已处理而回执丢失，或不支持幂等 | 可保证范围、核实方式及无法保证恰好一次的限制 |

## 8. 开放参数与技术 handoff

本轮已确定的是目标行为，不是数值、依赖或最终 schema。正文逐项列责任方、决定前置证据和实施 gate：

- DAA：支持 PLC 数量、CPU/驱动/访问模式/类型矩阵、最低周期、读取合并阈值、批次/队列/并发限额、上传速率与公平预算、退避策略。
- DAA 存储：实际样本/采集轮次粒度、配置摘要/分片完整性、SQLite 库与版本、schema/索引、天数/容量/最低余量/高低水位、WAL/checkpoint/回收策略、备份恢复与凭据安全存储。
- Backend：一个接收 API 的正式路径/版本/鉴权/响应、整体或部分确认、样本顺序与完整事实单位、唯一有效来源/代次交接、latest 质量策略、并发安全 feed、raw/去重/feed 保留。
- SMA：输入订阅/查询合同、完整边界/缺口策略、流程版本处理与重算、窗口暂定/修正、持久 checkpoint/outbox、各目标幂等与保留要求。
- 系统：关闭窗口/显式退出、后台运行、目标平台、安装升级、现场容量/吞吐测算及旧链路切换。示例数值均标示示例，不冒充默认或承诺。

本次文档与跨端范围采用 `aiis`、任务/入口治理采用 `project-governance`。需要冻结专门技术结论时，Development 先读取相应 skill 并确认是否仍属本 r1 文档范围；超出则回 PM。后续 DAA 实施路由 `rust-runtime`、`desktop-tauri`，点位算法加 `plc-point-mapping`，UI/文案加 `frontend-ui`、`i18n-workflow`；Backend 实施路由 `backend-arch`；SMA 路由 `rust-runtime` 并按 UI/API 表面组合相应 skill。不因讨论队列或重试恢复 Celery/Redis，也不由本任务替各会话执行技术工作。

## 9. 顺序、检查与停止条件

1. Human Owner 精确批准 `ARCH-AW-003 r1` 文档范围。主协调在 spec 存在后可机械登记 draft；不能预造 Development 或 QA 证据。
2. 命名 Development 读取完整 bundle、当前受影响文档和工作树，保护并发修改，创建正式正文；再做最小指向和双语入口同步。
3. Development 只执行文档覆盖/术语一致性、Markdown 本地路径/新增锚点/围栏/表格、双语入口对应及 scoped diff/whitespace 检查，记录真实命令、退出码、失败修正、未决项和未运行边界。未跟踪文件需全文/内容差异检查，不能以空 Git diff 代替验证。
4. developer_handoff 固定精确 r1、文档清单、工作树/基准/必要内容指纹、自检与限制、所创建资源。主协调启动新的 `verification`，使用 fresh context（工具支持时 `fork_turns="none"`），独立映射 AC 并记录文档 verdict；Verification 不静默修文。
5. 独立文档 QA 后交 Human Owner 最终验收。`qa_passed` 不表示原生运行、吞吐、数据库/API/PLC/SMA 能力已验证，不提供代码、发布或现场授权。

本轮不安装依赖，不运行工程构建/测试、应用启动、真实数据库/PLC、Docker、推送或发布；不为纯文档任务新增自动化测试。外部技术事实若用于正文，由 Development 只核验必要官方来源并就近引用；未验证的技术选型保留待决，不靠记忆定案。既有无关断链/文档漂移单列，不扩大修复。

主要风险是设计被误认成已实现、最新优先与批次确认混淆、跨组序号被误当连续输入、跨库激活崩溃、清理破坏重试、feed 漏读，以及外部 API 无幂等却宣称不重复。通过正文不变量、场景矩阵和各端待决 gate 控制。文档需要回退时仅恢复本任务新增内容/段落并保留并发改动，本轮不执行删除或回退。

发现必须新增可执行合同、schema/依赖、运行验证、改变职责或扩大 allowlist/验收/风险时，停止受影响部分，返回 PM 新 Revision 并重取 Human Owner 范围批准。
