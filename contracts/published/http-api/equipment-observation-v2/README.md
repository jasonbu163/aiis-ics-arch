# Equipment observation and energy machine ingest v2

[中文](README.zh-CN.md) · [OpenAPI](openapi.json) · [Synthetic requests](vectors.json) · [Private profile example](example-profile.json) · [Approved r10 spec](../../../../plans/ARCH-OBS-001-configuration-driven-equipment-monitoring/spec.md#r10-source-independent-energy)

Post-retirement source accepts only v2, rejects old v1 after authentication and authorization, and never replays archived receipts. Its private profile accepts only `d8f2a4c6b915`. The published vectors, OpenAPI and example profile retain their original version. [Retirement specification](../../../../plans/ARCH-OBS-002-legacy-observation-retirement/spec.md)

Equipment and process observations share the `observation_metric_*` configuration tables and write receipts to `observation_ingest_receipts`. Meter samples use `energy_ingest_receipts` independently. The migration preserves existing IDs and retry results.

This contract describes the r10 v2 payload and current operations. A private server profile binds each machine Bearer producer to allowed equipment, targets, groups, metrics and meters; the producer can be SMA, a third party or another authorized program. The request cannot grant access, and no PLC evidence is required. This does not establish that an SMA product has implemented delivery. Profiles are cached by the process and changes require a coordinated reload. The example target and hash are unusable placeholders; never commit a real token or private profile.

| Method and path (under `/api/v1`) | Purpose |
| --- | --- |
| `GET /integration/metric-definitions?equipmentId=...` | Discover the caller's authorized groups, metric types, units and target enablement; no sample values. |
| `POST /integration/equipment/latest-snapshots` | Replace the complete multi-group snapshot for one equipment/task when newer. |
| `POST /integration/monitor/history-samples` | Append the same bundle, retaining only history-enabled metrics and reporting stored/skipped keys. |
| `GET /integration/energy/metric-definitions?meterId=...&groupKey=...` | Discover enabled, authorized meter metrics, quantities, units and measurement modes. |
| `POST /integration/energy/samples` | Append one meter/group sample independent of tasks. |

POST bodies use `application/json` and are limited to 65,536 bytes. See [OpenAPI](openapi.json). Both device requests require `eventId`, `equipmentId`, string `taskNo`, original `observedAt`, and `groups`; history also requires `quality: "good"`. Omitted/null latest quality becomes `unknown`. Energy requires `eventId`, `meterId`, `groupKey`, `observedAt` and nonempty `values`; an interval metric requires both true interval boundaries in increasing order, and an event without interval metrics must omit them. Timestamps need an offset and must be losslessly storable at microsecond precision; the backend converts them to Shanghai time and never invents observed time from receipt time.

`contractVersion` defaults to v2, and `producerId` defaults to the authenticated producer but must match if supplied. `mappingId` and `mappingRevision` are optional as a pair; `sourceRefs` is optional sender-declared metadata, not verified provenance. Credentials and grants are configured once, while event ID and observations are provided per event. Retry with the same target, producer, event ID and original body; changed content conflicts with 409. A stored receipt is returned only while the producer retains current permission for the request and, for latest, the full replacement scope; revoked access is rejected with 403. An unknown commit outcome must be retried identically.

Stable region and metric keys, not editable display titles, identify values. Omitted groups, empty groups and `groups: {}` mean missing; full latest replacement requires permission for everything it can clear. Even empty groups must be registered and authorized. Unknown or unauthorized keys and wrong types reject the whole event without partial writes; `null` is not a metric value, while zero, false and an empty string are valid. Numeric values must survive JSON storage without loss. A real good-quality history event with all retained values missing remains a gap event when history is enabled; only a device with no history-enabled metric returns `no_history_metrics`. Distinct same-time history events remain distinct; an event ID is not a clock or proof of physical deduplication across senders.

The standard success envelope has `data.target`, `producerId`, `eventId`, `outcome` and `recordId`; device receipts can also include `stored` and `skipped`. Outcomes include `stored`, `stale`, `already_stored` and `no_history_metrics`. Common failures are 401 identity, 403 scope, 409 event/sample conflict, 422 validation and 503 unavailable or unknown commit. Machine discovery never grants sample-reading access. Human read/configuration/management APIs use separate permissions and device/meter scopes; see the [guide](../../../../docs/equipment-status-process-monitoring.md#r10-guide).
