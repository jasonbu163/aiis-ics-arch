## 3. BG-01｜三界命名与叙事：职责模型，不是目录设计

**状态：**名称、职责指导与最新工程边界保留。  
**来源：**[S0](#source-s0)、[S1](#source-s1) 第 3 节、[S2](#source-s2) 第一节。

| 缩写 | 正式全称 | 叙事别名 | 来源中提出的主要职责 |
|---|---|---|---|
| PW | Platform World | 人界 | 业务对象、规则、流程、工艺版本、权限与任务授权、业务事务、第三方集成 |
| AW | Automation World | 天界 | 设备连接、采集、技术语义映射、归档、监督、现场条件与受控执行 |
| AIW | AI World | 魔界 | 模型接入、检索、分析、推理、规划、建议与 AI agents |

原叙事的重点是：人界提出目标、承担责任与授权；魔界推演可能性；天界遵循明确约束执行。别名帮助讲述关系，不代表权力高低、价值高低，也不是安全等级定义。

一张订单进入平台，智能服务提出方案，平台完成业务审查，现场运行时检查条件后执行或拒绝，结果进入后续分析——这个例子解释的是职责协作，不要求每一张订单都经过 AI，也不要求每次交互都新增一跳网络请求。

AW 改称 Automation World，是按“承担什么职责”而不是“里面的程序叫什么”命名。AW 中仍可有 CA、DAA、SMA、HA、SA，AWB/AWC 也不必叫 Agent；AIW 中同样可能有 AI Agent。Agent 名称不能决定归属或授予设备权限。

**最新澄清：**三界是长期指导，不是暂时没建、但最终必须建的三层顶级目录。判断架构是否形成，不看是否有 `pw/aw/aiw`，而看职责与接口是否成立。现有目录可以继续保留；工程载体与概念边界允许采用不同名字。

**后续使用：**用于总纲、概念解释和设计评审背景。AW 的工程演进使用配套主文，不在本条目安排三界拆仓或部署。

## 4. BG-02｜多语言分工与 PW 的候选实现

**状态：**保存已有长期偏好和实现候选；不表示当前仓库栈已改变。  
**来源：**[S2](#source-s2) 第二节、[S3](#source-s3)、[S4](#source-s4) 第一节。

### 4.1 已讨论的默认方向

| 职责方向 | 来源中的默认偏好 | 条件式扩展 |
|---|---|---|
| AIW 智能计算 | Python；需要服务入口时使用 FastAPI | 按需要接入模型服务、算法组件或其他语言 |
| PW 工业业务平台 | C# + ASP.NET Core + FastEndpoints | Java + Spring Boot 作为未来企业生态兼容/替代实现 |
| AW 现场运行 | Rust runtime；有服务职责时使用 Axum | 厂商 SDK、驱动或嵌入式适配需要时使用 C/C++ |
| 业务/工程界面 | JS/TS + Vue 或 React；现场管理可使用 Tauri | 根据界面用途归属，不按“有人使用”统一划给平台 |

关键表达是 **“PW 是架构角色，.NET 是所讨论的参考实现”**，而不是“只有 .NET 程序才属于 PW”。同理，Rust 程序不自动等于 AW，Python 程序不自动等于 AIW。

现有 FastAPI 中的订单、权限与工艺业务，在仍由它承担时继续属于平台职责。把 Python 作为 AIW 默认方向不等于可以把现有业务模块改称 AIW 来代替迁移。

### 4.2 .NET 主线与 Java 条件选项

《C# 架构技术学习》提出：先把 .NET 作为 PW 主参考实现，Java 只在客户、团队或既有系统出现明确约束时考虑，不同时要求维护 FastAPI、.NET、Java 三套等价实现。

其意义是稳定职责与公开契约，让实现可以替换，而不是以语言数量作为架构成熟度指标。Java 选项留在背景资料中，不成为 AW 版本的前置工作，也不自动进入当前仓库任务。

来源曾用以下方向表达候选组合：

```text
已有平台实现：FastAPI + SQLAlchemy + Alembic
讨论中的 PW 主实现：ASP.NET Core + FastEndpoints + EF Core
未来可选 PW 实现：Spring Boot + Spring Security + JPA + Flyway
```

这些是来源里的组合示意，不是本轮确认过驱动、依赖和能力覆盖的部署矩阵。尤其现有数据库的迁移权威不能因另一语言的表格而被自动替换。

下表保留 S3 中的候选对照，供今后选型讨论。**它不是逐项完全等价声明，也不是本轮新增技术决定。**实际功能、版本、依赖和适用范围需另行核查。

| 能力 | Python 侧原对照 | C# 侧原对照 | Java 侧原对照 |
|---|---|---|---|
| Web | FastAPI | ASP.NET Core + FastEndpoints | Spring Boot |

## 5. BG-03｜建议、授权、执行与任务生命周期

**状态：**跨域协作建议；不是已经实现的任务合同。  
**来源：**[S1](#source-s1) 第 3.3、15 节，[S2](#source-s2) 第三、四节，[S4](#source-s4) 第三—五节。

### 5.1 来源中的协作链路

```text
人员 / 外部业务系统 → 平台业务请求
可选 AIW → 建议、方案或任务申请
                         ↓
                  PW 校验、授权、持久化业务任务
                         ↓
                  AW 接受执行责任并检查现场条件
                         ↓
                  设备执行 / 拒绝 / 结果待核实
                         ↓
                  PW 接收事实，更新业务状态
                         ↓
                  AIW 在获授权范围内分析结果（可选）
```

图示表达职责顺序，不预先决定调用方向、目录位置或网络连接发起方。没有 AIW，已经定义的业务与基础自动化可以照常协作；依赖某个分析结果的新业务仍可能等待或失败，不能因此宣称所有 AI 功能都有自动替代。

来源反复强调的区别是：

```text
提出建议 ≠ 业务授权 ≠ 接受执行责任 ≠ PLC 接收指令 ≠ 物理过程完成
```

平台批准后，现场仍可因设备状态、配置、资源冲突或其他已定义限制拒绝执行。AIW 不能通过把 JSON 标成“已批准”获得现实控制权。

### 5.2 持久任务与状态通知分开

早期建议是平台受理请求后保存任务，返回任务身份，再通过查询或通知跟踪进度。WS 通知用于提醒有新任务或状态变化，不替代任务的持久化记录。

曾讨论的示意状态包括“待审批、可领取、已领取、执行中、成功/失败”，以及“已拒绝、已过期、结果待核实”。这些名字不是已定枚举；必要的是区分申请、授权、接受责任和完成的不同事实。

领取会改变执行归属，不是普通无副作用查询。任务身份要与调用方、资源范围、配置兼容条件和有效期对应，不能只让请求自行填写任意 `agent_id`。

### 5.3 重试、超时与资源冲突

“执行者失联”不自动表示“设备没动作”。来源中的重要场景是：动作已发出，网络断开，平台未收到结果。此时不能仅凭领取/续租超时把同一物理动作重新发给另一个 CA。

未开始任务可以按合同重新分配；已开始且结果不明的任务需要结合本地执行记录、设备反馈和当前执行归属核实。稳定任务 ID 和数据去重帮助恢复，但不能单独保证物理动作恰好发生一次。

同一设备或冲突资源应有唯一有效的执行责任。提高排队优先级不等于允许抢占已执行动作；采集、不同设备和分析工作的并发规则要分别看实际约束。

高危本地操作不能改名为“任务”后绕过原有权限；本地操作、远程标准任务可以共用执行仲裁，但允许的动作范围不必相同。控制保护不能依赖普通 Web 请求成功。

**留在 AW 主文的部分：**现场校验、执行记录、禁止盲重试和后续 CA 边界。  
**留在本资料的部分：**建议如何进入平台授权、平台如何对外表达任务事实及三界整体闭环。具体实现待控制/平台专项决定。

## 6. BG-04｜PW 与 AIW 的分析、建议和反馈接口

**状态：**从 v0.3 移出的跨域设计建议，不作为 AW 主文的开发内容。  
**来源：**[S1](#source-s1) 第 12.6 节、[S2](#source-s2) 第二—四节。

| 交互 | 原建议保留的内容 | 仍需明确的部分 |
|---|---|---|
| PW 请求 AIW 分析 | 给出获授权的数据、目的和范围；长分析具有可查询身份 | 分析生命周期、时限、取消、数据最小化和失败处理 |
| AIW 向 PW 提交结果 | 建议、方案、参数候选或任务申请；不是设备执行命令 | 结果校验、版本、责任、人工确认与平台业务规则 |
| PW 接入 AW 能力 | 提交获授权工作或查询现场事实 | 与实际部署对应的 API、资源与身份合同 |
| AW 向平台提供事实 | 保留 AWB 查询/订阅与 SMA 主动投递 | 时间、质量、范围、确认、保留和重放 |
| AIW 取得后续反馈 | 默认通过平台或经平台治理的授权只读通道 | 可见字段、保留时限、访问记录和再使用边界 |

原建议优先保留 HTTP 请求与实时状态通知，不要求模型推理一直阻塞同一个 Web 请求。具体服务、队列、数据库和模型并未形成完整规格。

AIW 请求分析数据不代表它自动取得 AW Redis/PG 凭据、配置发布权或 CA 写入工具。只读订阅、建议提交和控制执行应分别授权。

AIW 失效不应阻塞既定 DAA 采集、SMA 映射、HA 归档。需要 AI 结果才能继续的新业务，应由对应平台策略处理等待、失败或人工接管；本资料不补造通用兜底算法。

**来源没有确定：**模型名单、RAG/向量库选型、AIW 数据库、AI Agent 团队、内部路由或部署规模。本次也不填写这些空白。

## 7. BG-05｜工程管理、业务授权与执行记录的区分

**状态：**v0.3 的解释性衔接，保留为进一步讨论的起点。  
**来源：**[S1](#source-s1) 第 3.5、6.4 节；上位依据是 [S2](#source-s2)、[S4](#source-s4)。

这一组内容是 v0.3 为连接中央 AWB 设计与三界叙事补充的解释，不应回写成“原始讨论已经确定了全部任务模型”。

| 权限/记录 | 原解释的责任侧 | 边界 |
|---|---|---|
| 业务目标、订单/工艺规则、业务任务授权 | PW | 不绕过现场条件，不假装设备已经执行 |
| 点位、映射、归档、配置发布和运行诊断 | AWC/AWB 工程管理 | 不因能修改配置就自动获得业务审批或任意设备写入权限 |
| 接受执行责任、领取、设备反馈与结果 | AW | 关联业务任务，但不再建立第二套业务审批权威 |
| 分析请求、建议和推理结果 | AIW | 分析身份不等同业务批准或现场执行 |

人通过 Tauri 使用 AWC，不意味着 AWC 因为“有人操作”就必须归入 PW。它是现场工程管理入口；是否允许某项操作仍需要自己的身份和权限校验。

同一个跨域任务可以在平台与现场各有记录，但记录的事实不同。来源尚未决定最终主键、状态映射、取消传播和一致性流程；不能仅用两个“任务表”就认为责任已经清楚。

平台暂时离线时，本地维护操作允许到什么程度，与已运行工艺如何安全结束是不同问题。配置发布、工程审批与业务授权需要区分，不能只相信一个 `local_approved: true` 字段。

**后续讨论重点：**如何证明授权来源、授权绑定何种设备与参数、配置变更是否影响在途工作、多个记录何者是每一种事实的权威。AW 主文只保留自己需要的边界，不在这里替各方选数据库模型。

## 8. BG-06｜连接方向与协议备选

**状态：**既有默认建议与条件式选项，不要求全部实现。  
**来源：**[S1](#source-s1) 第 12.5—12.7 节，[S2](#source-s2) 第三—六节，[S4](#source-s4) 第三、五、六节。

### 8.1 授权方向不等于连接方向

来源倾向先考虑现场主动连接平台、领取任务或投递数据，以减少每个现场程序的入站接口；同时保留网络允许时平台访问 AWB 受限入口的方案。

| 场景 | 来源中的选项 | 不改变的原则 |
|---|---|---|
| 平台可访问受控 AWB | HTTP 查询/提交与 WS 订阅 | 调用仍受身份、资源与动作授权约束 |
| 现场不允许跨区入站，但能向外建立受控连接 | 现场 HTTP 请求、SMA 主动投递、由现场建立的长连接 | 业务授权仍不由谁先建连接决定 |
| 单个 Rust 程序只需要主动领取/回报 | HTTP 客户端 | 不因此必须部署 Axum |
| 多个 runtime 需要中央配置/查询服务 | 中央 AWB | 不要求每个 Agent 开放自己的 Web 服务 |

连接由现场建立后，平台仍可以沿长连接发送通知。“推送消息”不等于“必须让平台向每台设备发起一个新的入站连接”。

主动连接只是减少一类暴露，不会让服务器返回的数据天然可信。对方 API 的内容、身份与参数仍需验证；localhost、CORS 或 Tauri capabilities 都不能替代自建 HTTP 接口的授权检查。上述均为原材料已提出的边界，不构成本次完整安全方案。

两种网络拓扑可保留为设计选项，但不能宣称无成本互换；证书、网络规则、恢复和资源配置仍需分别验证。

### 8.2 任务发现方式的历史比较

| 方式 | 来源中提出的理由 | 所需补充 |
|---|---|---|
| 周期领取 | 简单、容易排查 | 轮询间隔、空请求、超时 |
| 长轮询 | 有工作时可尽快返回，减少空轮询 | 连接、超时、取消与负载 |
| 长连接通知后领取 | 通知及时，完整任务仍持久保存 | 断线、重复提醒、补取 |
| 平台直接调用现场 HTTP | 明确的直接集成场景 | 每个入口的网络、身份与运维责任；非默认 |

任务复杂度与网络方向是不同问题，不宜仅以“简单动作推送、复杂任务拉取”分类。

### 8.3 HTTP、WS 与契约

来源的默认组合是 HTTPS + JSON 表达明确请求，使用 OpenAPI 描述 HTTP 接口；WSS 用于状态、事件和进度。正式任务持久化，通知不代替事实。

WS 仍需应用约定消息类型、请求关联、序列、错误、重连与补发。能建立 WS 连接不代表双方消息互通，也不等于断开期间的数据已被保留。

| 契约主题 | 后续需要回答的问题 |
|---|---|
| 身份与权限 | 谁可以查哪些数据、申请或执行哪些任务 |
| 任务/事件身份 | 重复消息如何识别，是否代表同一次操作 |
| 目标和参数 | 设备、单位、范围、工艺与配置版本是什么 |
| 状态和结果 | 申请、受理、授权、开始、完成各意味着什么 |
| 有效期与兼容 | 过期怎样处理，版本不同如何协作 |
| 顺序与追踪 | 断线从哪里恢复，旧值是否可能覆盖新值 |

各方内部可用自己的 DTO、模型和 ORM，跨界遵守公开契约。接口共同语言不等于内部数据模型共享。

### 8.4 可选协议的原建议

| 选项 | 来源讨论的适用位置 | 同时保留的限制 |
|---|---|---|
| SSE | 单向文本、分析进度或状态事件输出 | 重连能力不代替服务端事件保存与补发；已有 WS 满足需要时不必增加 |
| MQTT | 节点增多、遥测分发、多消费者、间歇连接 | QoS 确认不等于业务完成，QoS 2 不保证 PLC 动作恰好一次 |
| gRPC | 明确需要代码生成、内部流式调用或测量支持的性能优化 | 不因为多语言就默认引入，增加构建与调试责任 |
| SignalR | 平台与界面连接管理的条件选项 | 具有自己的消息协议，不可当作普通 WS JSON 直接互通 |

来源建议 HTTP 管理接口与业务请求可以继续保留，MQTT 在遥测/消息分发有具体需要时进入，gRPC 在某条内部链路有明确收益时局部评估。

本资料没有把这些选项升级成统一通信框架。技术描述来自历史资料；实现前需要重新确认所用版本、客户端和协议兼容性。

## 9. BG-07｜跨域数据所有权与两种数据交付

**状态：**已有边界及跨域解释；AW 实现细节在主文。  
**来源：**[S1](#source-s1) 第 6、12 节、[S2](#source-s2) 第六节、本会话对 TSS 的描述。

### 9.1 数据职责

| 数据 | 原讨论中的责任方向 | 跨域方式 |
|---|---|---|
| 业务对象、工艺审批、业务任务与业务事务结果 | PW | 业务 API/事件，不公开内部表和数据库账号 |
| 设备配置、点位、原始/语义采样与历史 | AW | AWB 视图或配置好的 SMA HTTP 输出 |
| 分析请求、建议、推理结果 | AIW 的职责范围 | 按约定接口协作；内部存储未选型 |
| 现场接收/执行与反馈 | AW | 关联业务任务，返回现场事实 |

用户提出的平台 Redis 主要用于登录 token 相关状态，AW Redis 用于实时工业数据，两者分开。这个具体使用意图作为背景保留，不把平台认证协议、会话方式或 token 类型定案。

AW 的中央 PostgreSQL 与平台项目数据库分开，是目标数据边界。平台按项目需要选型，不因 AW 用 PG 就被要求更换。AIW 的缓存、向量库和数据库没有在这些材料中形成最终方案。

### 9.2 查询与业务投递互补

一条通路是平台从 AWB 读取/订阅实时和历史状态；另一条是 SMA 向平台业务接口主动提交映射结果。前者主要满足查看状态，后者用于需要平台接收并办理业务的数据，两者可以并存。

TSS 作为来源，指用户描述的“映射后通过 HTTP 写入平台”原型。本次未审查其源码，不能据此宣称已完成可复用性验证。

两条通路不是“谁更先进”的替代关系。需要控制同一业务投影的写入责任，避免读取链路和推送链路都触发同一业务副作用。

### 9.3 接收方一致性的背景建议

v0.3 建议平台把去重与业务写入放在一个明确的事务中；这条建议从主文中移到此处，作为 PW 接入专题的候选实现。AW 主文只承诺交付事件身份、重试规则与接收合同，不指定平台内部表。

请求超时不能证明对方未处理。重试保持同一事件 ID，同一身份携带冲突内容需要拒绝或核查。状态型输出允许按契约合并过时快照，事实型输出不能静默丢弃；较旧重试不能覆盖已经接受的较新状态。

Redis 更新与平台写入不是一个原子事务。SMA 的 outbox、容量、重试及归档规则以 AW 主文为准；平台侧的事务与恢复作为自己的专题设计，不把两边混成一个共享数据库程序。

## 10. BG-08｜Axum 的职责与早期建议的适用范围

**状态：**来源适用范围说明；不改变主文中已经记录的 AWB 目标。  
**来源：**[S4](#source-s4) 第二、六、七节；[S1](#source-s1) 第 6.1 节及来源说明。

早期讨论针对的是“单个 Rust runtime 是否应该顺便加一层 Web 服务”。当程序只是请求平台、上报状态、订阅通知或供自己的 Tauri 界面调用时，客户端或本地 IPC 已有明确作用，因此当时建议不默认增加 Axum。

后来本会话给中央服务增加了配置、发布、查询、运行管理以及多 Agent 对接职责，AWB 因而有了独立的服务需求。目标采用 Axum 是这个职责变化后的选择，不等于要求所有 Agent 都带 HTTP 服务器。

| 两条来源表述 | 实际讨论对象 | 可同时成立的解释 |
|---|---|---|
| 不默认给每个 CA/runtime 加 Axum | 单个现场运行程序 | 主动请求与本地 IPC 不要求自建 Web 服务 |
| AWB 采用 Axum | 具有明确 API 职责的中央服务 | 用它提供配置、状态与管理接口 |

因此，后续检索不应仅摘录早期“Axum 默认不部署”，用来取消中央 AWB；也不应摘录“AWB 用 Axum”，就给每个采集/映射实例增加监听端口。

S4 还反对在没有测量依据时，预先建设 Rust 后端来“弥补 FastEndpoints 性能”。若慢在数据库、网络、锁或序列化，多加一个服务不自动解决问题。提取明确适合 Rust 的计算或协议能力是另一项决策，也不必然要求 HTTP。

Tauri 可以作为管理入口，但子进程并不自动具备 UI 关闭、用户注销、系统重启之后的持续服务保障。独立运行、配置恢复、进程托管与高可用分别设计；相关 AW 规则已在主文保留。

**来源缺口：**`Rust框架比较.txt` 的当前内容实际上是 v0.3 更名与修订回复，不包含一份可独立核查的 Rocket/Actix/Axum 评测。不能只凭文件名将它当作框架比较或维护状态证据。本资料不补造这类结论。

## 11. BG-09｜既有版本路线与三界长期方向：保留差异，不静默合并

### 11.1 已有两组不同的路线资料

v0.3 沿用的固定仓库记录显示，`ARCH-MULTI-001` 草案讨论了 1.x 的 .NET 方向、2.x 默认 Rust/PostgreSQL，以及平台前端、数据库支持和交付的工作。具体仓库记录固定于 commit `ac316ebabb65c1799a6b8f2e4fbd4096b5afc9ec`，本次未重新读取。

三界背景则提出 .NET 平台、Python 智能服务、Rust 自动化运行的长期职责偏好。两组内容讨论维度不完全相同，但**不能因此宣称它们已自动合并成无冲突的一条实现路线**。特别是“平台默认 Rust”与“.NET 为 PW 主参考实现”的关系，仍需将来在实际项目范围中明确。

### 11.2 最新修订的演进主线

用户最新澄清是：当前 AW 方向仍以 `control-agent` 的工程形态存在，后续逐步发展，不需要先在项目外从零建设全套 AW，再作为唯一方式接回原项目。

主文已经改为从现有工程发展能力的 Roadmap。独立试验工程仍可以作为验证方法，但不是新架构必须另建仓库的命令；同仓库和共享 workspace 也可以，只要实际新角色保持独立职责与生命周期。

“现在不建立三个顶层目录”不是暂时让步；最终也不以三个目录作为达标标准。达到目标是职责与边界逐渐完整，而不是某次目录搬迁完成。

### 11.3 版本与变更权威

文档 v0.4、未来软件版本、配置 revision、数据库 schema 与接口版本分别管理。本资料 v0.1 只是背景整理的版本，不代表任何软件发布。

现有工程中的 Alembic 与其他依赖边界不因候选技术表而改变。未来 AW 采用 SeaORM Migration、平台候选使用其他迁移工具，都需要在所属数据模型与具体任务中明确权威，不能对同一现役 schema 同时增加相互竞争的迁移者。

**后续议题：**确有需求时，明确旧路线哪些继续、哪些修订、修改哪个项目、如何保持兼容。这个问题是背景资料中的讨论线索，不是 AW 主文新增的一阶段开发工作。
