## 1. 文档范围与设计效力

### 1.1 本稿解决什么问题

本稿记录已有现场运行能力如何逐步发展为更完整、可独立运行和复用的自动化运行体系。重点不是为三界分别设计一套产品，而是保存本会话已经讨论清楚的 Rust 工程方向。

| 属于本稿 | 不在本稿展开 |
|---|---|
| Rust runtime、Axum 服务、SeaORM、Tauri 管理入口 | PW 的 .NET/Java 实现与迁移路线 |
| CAF、CU、DAA、SMA、CA，以及长期 HA/SA 的职责 | AIW 的模型、检索、算法、内部 Agent 或数据库 |
| 近期本地 SQLite、长期中央发布与配置回退 | 三界整体的组织、部署或多语言后端建设计划 |
| AW Redis、中央 PostgreSQL、历史归档 | PW 的会话、登录 token 与完整业务数据模型 |
| AWB HTTP/WS、SMA 主动 HTTP 投递等边界接口 | PW 与 AIW 的分析申请、建议生成和反馈工作流 |
| 现场运行故障、兼容与渐进验收 | 把三界命名转成强制目录或仓库布局 |

**与外部平台如何对接属于 AW 能力；替对方设计内部实现不属于本稿。**更完整的三界背景见配套资料，本稿不以其条目增加 AW 的开发任务。[U6]

### 1.2 指导模型、运行组件、目录布局分开

三界的最小背景是：PW（Platform World）承担平台业务职责，AW（Automation World）承担自动化运行职责，AIW（AI World）承担智能分析职责。它们是理解边界的上下文，本稿只展开 AW。

AW 中的 Agent 是采集、映射、归档、监督或执行角色，不等同于 LLM Agent。基础采集、映射与归档不需要等待模型服务；外部智能身份也不自动获得设备控制权限。除此之外的三界协作细节移入背景资料。[U4][D3 §3]

| 层次 | 本稿的约定 |
|---|---|
| 架构指导 | 根据职责、数据所有权和权限判断归属 |
| 运行边界 | 新角色首次正式实现时就具备自己的执行入口与生命周期 |
| 代码组织 | 同仓库、同 Cargo workspace、共享 crate、实际目录命名由工程需要决定 |
| 部署交付 | 可以同机、同安装包部署；不因此把所有常驻循环塞进一个 Tauri/Axum 进程 |

**不强制三界目录，不等于取消独立运行角色；保留独立角色，也不等于必须立即拆成三套系统。**最终应检查职责是否清楚、依赖是否合理，而不是检查文件夹是否叫 `aw`。

### 1.3 当前事实、确定方向与长期目标

### 2.2 CAF 与新 CA 的命名分开

2026-10-15 的命名决定是：原 CA 使用 **CAF** 表示冻结参考身份，新 **CA / Control Agent** 专指设备控制执行。CAF 未确认的英文展开不在本文创造。[U7]

只读核对时，仓库仍存在 `automation-world/control-agent/`，其 README 保留冻结采集与快照合同；也已存在 `automation-world/console-ui/` 目录，但其中 README/PLAN 仍沿用旧 CA 文本。目录存在不证明新 CA 控制闭环、CU 共享包或设计工作台已经交付。用户说明老 CA 已移出；精确迁移路径和源码事实由对应任务核对，本轮不认证迁移或改写历史 receipt。

| 来源/角色 | 定位 |
|---|---|
| CAF | 原 CA 冻结参考；采集、诊断、视觉等素材按明确任务复用，不成为活动共享运行时 |
| DAA | 已有独立采集工程；后续改为本地配置驱动的 S7 读取与事实 API 上报 |
| SMA | 已有独立 HTTP 映射工程；后续语义加工与对外投递 |
| 新 CA | Tauri 管理入口 + 独立 Rust 执行角色；持久意图、写设备、握手与回执待实现 |
| CU / console-ui | 共享 UI 源码和可运行设计工作台的设计定位；各 Agent 构建引用，运行无需工作台在线 |

CAF 不是新 CA 的另一运行模式。继承素材不等于延续旧直库权限，也不改变冻结工程的历史验收范围。

### 2.3 不改变现有工程的迁移与依赖权威

旧稿记录的工程契约要求数据库结构变更走显式 Alembic/schema-maintenance 任务，恢复 Redis 等组件需要单独批准。未来 AW 选择 SeaORM Migration 和专用 Redis，不改变这个当前边界。[R2]

目标中的 `agent.toml` 和双配置槽，也不授权立即替换当前 `.env`/YAML。现有平台多后端路线单独管理，本稿不为它重排语言、版本与日期；相关背景和潜在衔接问题放入配套资料 BG-09。

### 2.4 演进的评价标准

本稿关注的是：现场能力是否更容易复用、配置是否可控、独立运行是否可信、数据交付是否清楚、维护成本是否可接受。只有真实需求和对应任务需要时才增加组件；不以“凑齐三界”作为启动理由。

## 3. Rust 目标组件与技术选择

### 3.1 组件角色

| 缩写 | 全称 | 目标职责 | 不承担的职责 |
|---|---|---|---|
| AWB | Automation World Backend | 中央配置、发布分配、身份管理、运行管理接口、实时/历史 API；未来执行任务接入 | 不运行 DAA/SMA/HA 的常驻核心循环 |
| AWC | Automation World Console | Tauri 点位、映射、归档、投递、更新、诊断与生命周期管理界面 | 不直写数据库，不成为 Agent 的存活前提 |
| CAF | 未确认英文全称 | 原 CA 冻结参考工程 | 不作为新 CA 或活动共享运行时 |
| CU | console-ui | 共享组件、布局、主题及 UI 设计工作台 | 不拥有 Flow Core，不直接操作 PLC，不成为在线依赖 |
| DAA | Data Acquisition Agent | S7 点位配置、采集、解码、时间/质量及事实 API 上报 | 不编排业务流程，不承担设备下发 |
| SMA | Semantic Mapping Agent | AW 事实转语义对象并向第三方/上层 API 投递 | 不写 PLC，不直连业务库，不代替接收方业务校验 |
| HA | Historian Agent | 原始采样默认归档、语义结果可选归档、批量持久化与保留 | 不复制平台的业务表，不代行映射 |
| SA | Supervisor Agent | 健康、业务进展、依赖诊断、受控保活和生命周期管理 | 不默认获得设备写入权，不自动等同冗余主备 |
| CA | Control Agent | 领取本系统持久有效意图、现场校验、资源仲裁、设备下发及确认回执 | 不从任意外部 URL 直取数据写设备；实现另行立项 |
| DS | Device Simulator | 开发、测试与联调的设备模拟工具 | 不是生产 Agent，不是 DAA/SMA/CA 生产依赖，不证明真实设备行为 |
| Backend | 本系统 API 宿主 | 接入校验、持久意图、事实 API、原子领取与回执、内部存储/schema | 不在请求线程运行 PLC 常驻循环 |

AWB/AWC 的正式展开使用 Automation World；角色名称和 `agent.toml` 保留 Agent。以上是长期角色图，不是本版必须同时交付的程序清单。[U1][D3 §4]

### 3.2 独立边界从新角色的首次实现开始

新增某一角色时，按该角色自己的入口、配置、生命周期和发布能力交付。允许共享模型、协议适配、配置加载、日志及其他基础 crate；不采取“把所有 Agent 先写在一起，以后再拆”的新实现路径。

这项约束适用于未来正式引入的新角色，不把已有工程状态追认为违规，也不要求本轮拆除已在工作的 `control-agent`。尚未实现的角色保留设计即可。

### 3.3 技术方向

| 对象 | 已讨论的目标选择 | 本稿保留的边界 |
|---|---|---|
| 常驻自动化程序 | Rust；异步工作按需要使用 Tokio | 具体版本和协议驱动在实施时验证 |
| AWB HTTP/WS | Axum | 提供中央接口，不要求每个 Agent 内嵌 Axum |
| AWB 常规数据访问 | SeaORM | 不以裸写 SQLx 为默认业务开发方式 |
| 未来 AW PG schema | SeaORM Migration | 唯一受控迁移流程，不接管当前项目 Alembic |
| 工程控制台 | Tauri + Web 前端 | 配置与管理入口，不承担所有后台循环 |
| 中央持久化 | PostgreSQL | 配置、元数据、历史按职责授权 |
| 本地持久化 | SQLite | DAA 近期配置权威；SMA/CA 建议沿用；运行记录独立管理 |
| 实时数据 | 独立 AW Redis | 最新状态与选择采用的记录流 |
| 后续消息机制 | 按需要引入 MQTT | 不要求第一步同时实现所有消息通路 |

SeaORM 在底层使用 SQLx 驱动不意味着业务层必须直接编写 SQLx 查询。迁移与实体管理仍属于所选 SeaORM 工具链；不将自动 schema-sync 设置为生产默认。上述解释沿用旧稿技术参考，本次没有重新检查库版本。[T1][T2]

Rust 程序主动领取配置、投递数据，只需要相应客户端能力；AWB 之所以用 Axum，是因为中央接口已有明确职责。**“不为每个 runtime 默认加服务器”与“目标 AWB 使用 Axum”并不冲突。**[U3]

## 4. 近期数据关系与长期存储方向

近期最小链路为：

```text
各 Agent 的 Tauri UI → 本机 Rust 配置服务 → 自身 SQLite → 有效内存配置
设备 → DAA → Backend 事实 API → SMA → 第三方/上层业务 API
第三方/上层 → 本系统 API 校验并持久化 → CA 原子领取 → 设备写入/确认
                                               CA → 本系统执行回执
```

DAA 获取事实，SMA 向外表达事实，CA 向内执行意图。“对外/对内”描述业务责任：SMA 可以 GET 材料，CA 可以 POST 领取、心跳和回执；CA 回执由自身完成，不依赖 SMA。

Agent 不直接持有 Backend 业务库或 Redis 凭据，也不依赖任意表名/SQL。Backend 可调整关系库、缓存或历史存储，但不能静默降低 API 成功回执的可靠性。Redis 不属于本轮部署，也不能替代可靠执行意图的真相源。

### 4.1 长期独立 AW 的关系

按项目需求，未来 AWB 可以承接中央配置、身份、实时/历史接口，HA 管理获授权的归档，SA 管理健康与有限生命周期。原稿中的 PG 配置/历史、独立 AW Redis latest/记录流均是长期方向。[D3]

若将来启用独立 AW 存储，AWB 拥有模型与迁移，HA 可用受限身份写自身历史表；其他 Agent 获取中央配置经过 API。外部平台消费公开合同，不共享内部表。AW Redis 与平台 Redis 的实例、凭据、资源及保留策略届时单独设计。

latest 不等于完整历史；独立 Redis/PG 不自动带来持久交付或事务保障。当前阶段不要求 DAA 直连 Redis，也不要求先建 AWB、PG、HA/SA 才能实现采集 API 闭环。

## 5. 近期本地配置与长期启动契约

### 5.1 一个业务配置权威

DAA 本版配置明确保存在本地 SQLite；SMA/CA 建议复用相同生命周期，各实例独立库和目录。点位、映射、流程、端点及采集/上报周期通过 Rust 配置服务管理，Tauri UI 使用受控 command，不直接编辑打开的数据库文件。

不形成 env、YAML、SQLite 多个可编辑业务配置权威。现有 env/YAML 合同继续作为历史基线，后续通过显式导入、预览和启用迁移，不在启动时静默覆盖用户配置。凭据保留引用，具体安全存储待决。

### 5.2 长期 `agent.toml` 部署约定

原稿统一 `agent.toml` 文件名的方向保留为未来独立运行部署合同：实例身份、服务地址、SQLite 路径、日志和凭据引用按角色 schema 定义；不是统一所有角色的业务内容，也不把点位和流程放回另一份可编辑 TOML。

未来可采用显式 `--config` 优先、相对路径锚定选中文件目录的约定，但查找/覆盖顺序和 CLI 尚未实现，不改变当前工程自己的 env/profile 隔离规则。`Cargo.toml` 仍仅管理构建依赖。[T3]

### 5.3 编辑、生效与回退分开

近期建议 `draft → 校验/预览 → active → previous`。draft 是编辑区，active 是当前运行完整快照，previous 是上次切换出去且需兼容检查的版本。草稿保留量、schema 和切换恢复策略在后续任务确认。

第 7 节 current/previous 是原稿长期“两个稳定运行槽”合同；active 与 current 概念对应，但本地草稿不是已经批准的第三个运行槽。不能将两种命名直接写成已实现的精确 schema。详见[原理设计](AIIS_AW_Runtime_Design.md)。

<a id="central-config"></a>
## 6. 长期中央配置：不设固定版本上限，由 AWC 管理

本节在需要中央发布时适用；近期配置权威是各实例 SQLite，不要求本节先行建设。

### 6.1 存放版本记录，不按版本建物理表

中央 PostgreSQL 可以管理多个配置集和任意数量的版本记录，不再设置“最多五个”的产品规则。不是每发布一个版本就创建一张新的点位物理表。

各版本至少有配置集身份、revision、内容摘要、schema 版本、发布状态与分配信息。实际实体和表名在未来 schema 设计中决定。

### 6.2 草稿、发布、分配与生效分开

目标流程为：

```text
编辑草稿 → 校验 → 发布不可变 revision → 分配给实例
        → 显式请求同步 → Agent 接收并校验 → Agent 实际启用
```

草稿可编辑、删除；已发布内容变化生成新的 revision。修改版本说明等元数据不应改变该 revision 的实际配置内容。

“已发布并推送”不等于“现场已经启用”。AWC 应分别展示已发布、已请求下发、已接收、当前运行以及失败原因。

### 6.3 最低保留与删除保护

每个**在用配置集**至少保留一份有效已发布版本；不能把“至少一份”解释成整个 AW 所有设备只剩一份配置也合规。

AWC 提供管理与删除入口，AWB 执行服务端保护。建议保护以下引用：在役实例 `current`、`previous`，尚未完成的发布分配，以及将来受控任务使用的配置版本。

不同实例可能使用不同版本，所以实际受保护数量可以大于一。这是引用完整性要求，不是重新设定保留上限。

实例离线或状态不确定时，不因其心跳消失就静默释放引用。先进行重新同步、迁移或明确退役，再处理删除。已退役配置集的最终删除与历史保留由独立策略管理。

中央不自动删除现场 SQLite，也不通过删旧版本强迫运行中的 Agent 自动更新。

### 6.4 不同版本维度独立

| 版本维度 | 内容 | 本轮规则 |
|---|---|---|
| 文档版本 | 白皮书修订 | v0.4，不对应软件发布 |
| 程序版本 | AWB/AWC/各 Agent 可执行程序 | 按各组件发布与兼容矩阵管理 |
| 数据库 schema 版本 | PG/SQLite 表与迁移 | 保留需要的升级历史，不随配置删除 |
| 配置 revision | 点位、映射、策略等发布内容 | 中央不限固定数量；本地 current/previous |
| 数据契约版本 | API/事件/归档载荷结构 | 单独声明兼容性 |

<a id="local-config"></a>
## 7. 本地配置生命周期与长期 current / previous 双槽

近期采用本地 SQLite 编辑/应用方向；draft 保留与 active/previous 切换细则待定。以下双槽规则保留为长期发布合同，限制的是稳定运行配置快照，不限制运行记录或直接决定本地草稿策略。

### 7.1 只保存自身需要的完整配置

在采用长期双槽合同后，需要点位、映射、归档或监督策略的 Agent，在自身 SQLite 中维护两份完整运行配置快照。CA/DAA 可能需要点位；SMA 需要点位关联和映射；HA 需要归档策略；SA 只需要其监督配置。

不要求每个角色复制同一张完整 PLC 点表，更不复制整个中央数据库。没有此类配置需求的组件，也不为了形式统一而创建空的点位库。

稳定状态最多两个槽：

- `current`：当前启用配置。
- `previous`：上一次切换出去的配置。

`previous` 不是按版本号排序的“次新版”，也不无条件保证适配当前程序。启用前仍要校验兼容性。

### 7.2 更新与回退语义

| 操作 | current | previous |
|---|---|---|
| 首次启用 v1 | v1 | 无 |
| 更新 v2 | v2 | v1 |
| 更新 v3 | v3 | v2 |
| 显式回退到 v2 | v2 | v3 |
| 显式重新启用 v3 | v3 | v2 |
| 再更新 v4 | v4 | v3 |

推荐使用完整 snapshot 与两个引用，而不是为每个字段增加 `previous_address`、`previous_type` 等列。点位新增/删除、映射关系和策略应作为一个配置集合切换。

### 7.3 先准备和验证，再轮换

```text
本地 UI / CLI 显式请求指定 revision
    → Agent 取得本地候选（长期中央发布时下载候选包）
    → 校验实例归属、完整性、schema、程序兼容性
    → 准备新的内存配置
    → 等待允许的批次边界或安全切换点
    → SQLite 事务内轮换 current / previous
    → 提交后切换内存
    → Agent 上报实际生效状态
```

不能先覆盖 previous 再下载新包。下载或校验失败时，原有两份配置必须不变。

候选内容可以临时保存在内存或暂存文件；这不扩大为第三个长期保留槽。SQLite 事务用于避免配置表更新一半。[T4] 内存启用不是数据库事务的一部分，实施时必须定义暂停、恢复与崩溃重启处理，不能把事务提交直接当作运行切换完成。

正常启动只读取本地 current；中央暂不可达不清空本地配置。没有有效配置时进入待配置状态，不自动猜测设备地址。正常启动不追随中央最新版本。

### 7.4 唯一写入者与幂等操作

运行中的 Agent 是自身配置的写入者。Console/CLI 发管理请求，不直接覆盖一个正在打开的 SQLite 文件。[T5]

示意命令由未来项目实现：

```bash
aiis-daa run --config ./agent.toml
aiis-daa config update --config ./agent.toml --revision rev-0042
aiis-daa config rollback --config ./agent.toml --target-revision rev-0041
```

更新同一个 revision 且内容摘要相同应为无副作用确认，不再次轮换。回退指定目标 revision，不发送含义不稳定的“再交换一次”。请求重试时若已经运行目标版本，不得又切换回来。

Tauri 按钮和 CLI 复用同一套配置操作逻辑；运行时通过受控 IPC/管理通道办理，停机维护时确保独占访问。跨机器操作由被授权的本机管理组件执行，不把本地按钮当成天然远程进程权限。

### 7.5 配置回退不等于运行数据回退

点位、映射和策略可以轮换；outbox、消费进度、待补传数据、执行事实与审计不能因此删除或回退。它们应与配置按表或独立库分开管理。

同一个 SQLite 文件的两份配置只能提供配置级回退，不能承诺磁盘损坏、文件整体丢失或主机故障下的容灾。[T5]

未来中央发布不可用时，经过本地授权的回退可以使用已保存的 previous；实际状态恢复联网后补报。不因为上报失败就把旧值冒充成已同步的中央状态。

<a id="acquisition-mapping"></a>
## 8. 采集与映射：最新状态和记录流分开

### 8.1 DAA 的目标运行方式

近期 DAA 从自身 SQLite 加载明确启用的配置，固定执行读取、解码、质量标记和事实 API 上报；无需低代码流程画布。首版限西门子 S7 方向，具体 CPU、驱动、访问方式和类型支持矩阵待实施确认，不宣称支持全部 S7。

支持导入 TIA `.db`/`.udt` 文本源、单点编辑，以及手动整 DB 偏移推算。推算须提醒 DB 与全部嵌套 UDT 完整；检查字段顺序、支持类型、数组/字符串和对齐，缺失或不支持时拒绝猜测。绝对地址仅用于标准非优化 DB，以完整结构计算而非仅选中的点。先预览影响并确认保存草稿，再独立应用；结构编辑标记受影响偏移待复核。输入完整不证明匹配 PLC 当前程序，必须与 TIA 实际偏移核对。`.db` PLC 源与 SQLite 文件是不同工件。

设备连接、分组、采集、超时、重连和上报周期分别配置。`latest` 合并与 `samples` 批次交付属于待决模式，轮询不保证捕获采样间全部短脉冲。长期启动文件/中央更新分别按第 5—7 节评审。

DAA 的输出分成两类：

| 输出 | 含义 | 使用者 |
|---|---|---|
| 原始 latest | 每个点位/设备的最后已知状态 | SMA、AWB 诊断与状态查询 |
| 原始采样记录 | 已实际采到的样本或按契约保留的变化 | SMA、HA，及后续明确授权的消费者 |

raw 在这里指“尚未映射成业务语义的结构化采样”，不是默认保存完整网络报文字节。

数据库或平台慢不能无限阻塞采集循环。具体采用背压、丢弃、合并或本地缓冲，必须按数据类型说明；未实现缓冲时，不宣称 API 断开仍不丢数据。

### 8.2 SMA 的目标运行方式

SMA 读取自身有效配置中的点位关联、字段类型、转换与映射规则，从 AW 的原始数据取得输入，产生稳定的语义对象。

例如，输入点位 `tag_temp_001` 对应设备温度；输出可以是 `equipment.temperature`，而不是平台的某张 SQL 表某一列。SMA 知道公开的目标字段契约，但不知道 PW 数据库方言与内部表结构。

长期扩展时 SMA 可以同时输出语义 latest、供归档的语义记录，以及配置好的 PW HTTP 投递；近期先完成语义加工与第三方/上层 API 投递。三者分别记录完成状态，不假设它们是一个跨系统事务。

### 8.3 变化驱动与周期刷新

建议保留以下运行原则；具体阈值在项目配置和验收中确定：

- 状态、布尔和枚举在值或质量变化时及时更新。
- 模拟量可配置变化阈值，并保留最大刷新间隔。
- 每次重新处理旧数据，不得把处理时间改写成新的采样时间。
- 报警、重要状态转换和动作确认不能只靠覆盖 latest 保存。

每条数据建议携带来源、点位/设备身份、采样时间、质量、顺序标识和相关配置 revision。映射结果保留原采样身份，同时增加映射规则身份；多个不同时刻采集的点位合并后，不虚构成同一采样时刻。

### 8.4 两秒提交不等于两秒采样

若已采到 `0 → 1 → 0`，而 HA 两秒后只读 latest，就只能看到最后的 `0`。因此必须分别定义：采样周期、latest 刷新、映射批次、HTTP 投递节奏、历史提交间隔、界面刷新周期。

需要保存每条已采样记录时，可使用追加事件流再批量持久化。Redis Streams 是既有讨论中的候选实现；SMA 与 HA 需要完整输入时各用独立消费者组，不能在同一组内分摊后又以为各自取得全部数据。[T6]

如果只要求周期状态快照，可以明确选择 latest 定时归档，但必须标记为快照级历史，不能声称完整保留期间所有变化。

### 8.5 MQTT 的后续位置

MQTT 保留在后续消息机制路线中，可用于通知、事件分发或经过定义的跨节点通信。主题、ACL、QoS、会话、重连和消息过期等在实施契约中决定。

MQTT、Redis latest、Redis Streams、PostgreSQL 分别解决不同问题。不会因为引入 MQTT，就自动得到历史库、业务幂等或设备动作恰好一次的保证。

目标设计允许替换某条消息传输，但不要求第一轮同时接上所有中间件；未实现的消息路径不进入发布能力清单。

<a id="awb-interfaces"></a>
## 9. 长期 AWB 的服务面与数据视图

近期由本系统 Backend 提供所需事实、持久意图和回执 API；本节独立 AWB、Redis/PG 查询与中央配置属于后续方向。

### 9.1 配置和运行管理

AWB 负责配置集、revision、发布分配、Agent 身份、配置接收/生效状态和管理审计。Agent 通过它获取自己的配置，不直接从中央数据库全表拉取。

管理指令和设备控制任务不是同一种权限。触发更新、请求停止 Agent、调整采样参数和未来向设备下发工艺，都应有各自明确的授权范围。

AWC 的工程配置权限不自动变成设备执行权限。AWB 若在未来接入受控任务，需要独立定义任务身份、授权范围与执行事实；本稿只保留 AW 侧边界，不展开外部平台的审批实现。

### 9.2 查询接口

AWB 从 AW Redis 读取当前状态，从 AW PostgreSQL 读取历史，按已批准的视图输出给 PW。外部查询不触发每次即时 PLC 读取，不直接公开任意 key 和内部表名。

AWC 中可以配置一个命名视图，例如某条产线所需的温度、速度与状态。固定 API 读取指定视图，PW 不必知道点位源地址或 Redis 布局。

接口形态示意，非已实现路由：

```text
GET /api/v1/views/{view_id}/latest
GET /api/v1/views/{view_id}/history
WS  /api/v1/stream
```

同一视图需明确字段类型、单位、质量、新鲜度和授权范围。视图编辑器不是任意 SQL 或任意 Redis key 查询工具。

### 9.3 HTTP 和 WS 的语义

HTTP 轮询可以满足部分刷新要求；WS 用于持续订阅，但不自动提供断线历史重放或业务确认。[T7]

目标协议应包含初始快照、后续增量、顺序/缺口检测与重连重同步。实现时要处理“快照生成期间又发生新变化”的衔接，不只写一句“先快照再增量”就算完成。

AWB 需要主动实现事件/通知到 WS 广播的桥接。接口存在并不意味着 Redis 改值会自动触发消息发送。

### 9.4 缓存缺失与过期

Redis 没有值或最后样本过期时，可按接口策略返回历史最后已知值，但必须明确历史来源、原时间和过期状态。未知、离线、采集失败和缓存缺失不能全部伪装成数值零。

前端的实时显示应以数据时间与质量判断，而不是仅以 HTTP 200 或 WS 仍连接判断。

<a id="external-interfaces"></a>
## 10. 对外数据接口：读取、订阅与主动投递并存

近期事实/投递由本系统 Backend API 与 SMA 对接；通路 A 的独立 AWB/Redis 查询和通路 B 的多输出存储是长期扩展，不能作为当前 API 上传的必需依赖。

### 10.1 通路 A：PW 读取 AW 状态

```text
设备 → DAA → SMA → AW Redis 语义状态
                         ↓
                        AWB → HTTP / WS → PW 后端 → 页面
```

用途是回答“现场现在怎样”。数字孪生或 L2 页面可以通过 PW 后端消费视图，不必将每一帧再保存到业务库。

默认由 PW 后端持有对 AW 的服务身份；不要求普通浏览器持有 AW Redis 凭据或全域管理 token。

### 10.2 通路 B：SMA 主动向 PW 投递业务可消费数据

```text
SMA 生成语义数据
    ├── 更新 AW 语义 latest
    ├── 输出语义记录（HA 按开关归档）
    └── 可选 HTTP 输出 → PW 接入 API → PW 校验/去重/业务事务 → PW DB
```

此路径保留用户描述的 TSS 原型思路：映射后通过平台 API 写入，而不是由采集/映射程序直连平台业务库。

原稿 TSS 来源是用户描述；后续 ARCH-AW-001 已记录过滤复用与独立启动证据。该证据不证明新事实 API、SQLite 或共享流程已经接通。

该能力在目标中属于 SMA 的可配置 HTTP 输出模块，不需要额外创造一种 Agent。SMA 主动发请求只需要客户端，不因此内嵌 Axum。

### 10.3 选择规则

| PW 的需要 | 目标通路 |
|---|---|
| 展示当前状态，不需业务落库 | AWB HTTP/WS |
| 查询历史趋势 | AWB 历史接口 |
| 接收事实、关联业务、保存业务记录 | SMA → PW HTTP |
| 同时展示和办理业务 | 两条通路并存，但每个业务投影只有明确的一条写入责任链 |

SMA 的映射可以依赖公开接口契约，不能传任意 SQL、任意业务表名，或借“字段映射”绕过 PW 的权限与业务校验。

### 10.4 PW 故障不能堵死采集与映射

映射、Redis 更新和 PW 投递需要解耦执行，并配置限额、重试和可观测的积压状态。一个目标 PW 不可用时，不应无限阻塞其他目标或 DAA。

**最新状态型**输出可以按协议合并未发出的过时快照；**事实事件型**输出需要持久待投递记录，不得静默合并丢失。

可在 SMA 自身 SQLite 的运行状态表中记录 outbox。需要可靠投递时，先持久化输出意图再确认输入处理完成；配置轮换不清空该表。

请求重试保持稳定事件 ID；接收方应通过接口约定保证重复请求不重复产生业务结果。超时并不证明对方未执行；相同 ID 携带不同内容需要拒绝或核查。[T8] 接收方的数据库事务、去重表和内部服务组织不在本稿设计；本稿只记录 AW 所依赖的交付契约。

较旧状态延迟重试时，不应覆盖较新状态。事件顺序、源重启后的顺序标识、受理确认点和死信处理都列入未来接口验收。

这是一致性可恢复的多输出设计，不是 Redis 与 PW 数据库的原子双写承诺。

### 10.5 接口边界止于对接契约

本稿定义 AW 提供/消费什么数据、确认意味着什么、断线如何恢复，以及允许访问哪些资源。它不规定平台必须采用哪种 Web 框架、认证实现或业务表。

AWB 提供 HTTP/WS 不代表现场必须开放任意入站网络；SMA 主动投递也不代表可以访问任意 URL。实际网络路径、目标、凭据与资源范围需要受控配置。第三方仍通过约定的平台入口参与，不因此取得 AW 内部存储或任意设备写入能力。

双方需要记录接口/载荷版本、事件身份、时间、质量、顺序、确认点与错误语义。需要时采用既有讨论中的 HTTPS/WSS 和 HTTP 接口描述；不要求本稿顺带实现所有跨语言协议。更广的网络拓扑、AI 分析接口及协议备选见[背景资料 BG-04—BG-07](AIIS_Three_Worlds_Background_Notes_v0.1.md#bg-04)。

<a id="historian"></a>
## 11. 长期 HA：原始默认归档，语义可选归档，JSON 载荷

HA/PG/Redis 归档不是近期最小闭环依赖；以下默认仅在未来该能力获批启用后适用。

### 11.1 归档职责

未来 HA 启用后，默认归档 DAA 的未映射采样；映射后的语义数据归档默认关闭，需要通过配置显式开启。

```text
DAA 原始记录 ─────────→ HA 原始归档
      │
      └→ SMA 语义记录 ─→ HA 语义归档（可选）
```

SMA 停机或映射失败，不得导致已经采到的原始记录没有独立归档通路。HA 不从 PW 数据库反向复制订单或生产业务表。

配置示意：

```json
{
  "archive_raw": true,
  "archive_semantic": false,
  "retention_months": 3
}
```

开关默认对生效后的记录起作用；历史回填是单独操作，不因打开开关就自动恢复已经没有保存的语义结果。

### 11.2 JSONB 档案模型

用户确定以 JSON 方式归档；沿用前稿的实现建议，PG 使用稳定的档案结构，载荷字段用 JSONB，常用筛选元数据单独成列。[T9]

| 元数据 | 用途 |
|---|---|
| 事件/记录 ID | 识别与去重 |
| raw / semantic 类型 | 区分归档对象 |
| 来源、设备、点位集/视图身份 | 定位和授权 |
| 原始采样时间与归档时间 | 时间查询与延迟分析 |
| 配置 revision、映射 revision | 解释来源 |
| 数据契约 schema 版本 | 载荷兼容性 |
| JSONB payload | 一次有界采样帧或语义对象 |

这不意味着最终已经确定一张表还是多张分区表；也不为每个 PW 的每张业务表动态创建对应实体。

JSONB 不保留原始 JSON 文本的所有字面形式；需要原始报文字节时另行定义载荷。[T9] 异常质量、无效数值和大整数的跨语言表达也应在契约中规定。

### 11.3 批量提交与保留期限

原讨论中的“每 1—2 秒写入 PG”保留为可配置批量提交思路，不设为所有现场的硬性采样间隔。HA 消费记录后，持久化成功再确认；重复消费通过记录身份处理。

三个月保留是默认业务意图，不是容量保证，也不适用于配置和审计的统一删除。实施前按点数、频率、每帧大小、是否双份归档、索引及查询要求测算；“三个月”是日历月还是固定天数，应明确配置语义，不在文中擅自等同。

时间分区和分区清理可作为实现选项。[T10] 对 Redis 流的裁剪、持久化和故障窗口也需单独配置；使用 Streams 不自动等于零数据丢失。[T6][T11]

### 11.4 配置保留与历史可解释性

中央虽然不设版本数量上限，仍允许受控删除，因此不能无条件承诺任意历史数据都能按当时完整规则重新映射。

归档记录保留 revision/hash 可以识别来源，但摘要不能重建被删除的内容。若项目需要精确重放，应在实施阶段单独选择保护历史引用或随档案保存规则快照，不将这一额外能力假设为已经实现。

<a id="operations"></a>
## 12. 无界面运行、AWC 与 SA

### 12.1 AWC 是入口，不是存活条件

AWC 不存在或关闭，已经独立托管的 Agent 仍应按本地有效配置运行。Tauri 可以帮助启动程序和进行本地管理，但“独立子进程”本身不保证关闭界面、注销用户或主机重启后的持续运行。

未来部署需设计操作系统服务托管或其他明确的进程管理方式；具体 Windows/Linux 目标、安装形式和服务账户由实施任务确认。

近期各 Agent UI 通过本机 Rust 配置服务编辑 SQLite；长期中央 AWC 编辑配置调用 AWB；本机启动、停止、更新等操作通过被授权的本地服务/IPC；远程管理由目标机器上的授权组件处理。不从中央 Web 接口直接获得任意命令执行能力。

### 12.2 SA 的初始职责

SA 监督的不只是 PID，还包括最近成功采样、映射进度、归档进度、数据积压、配置版本和依赖状态。

依赖服务故障时，应能区别“Agent 自身异常”和“外部依赖不可用”，避免无上限重启。SA 自己由底层服务管理机制托管，不无限增加“监督者的监督者”。

初始能力为受控保活、诊断、告警与有限生命周期操作；不承诺自动无缝主备切换。

### 12.3 冗余接管是独立能力

心跳失联可能只是网络分区。对未来 CA，备用实例不能仅凭超时就取得同一设备的写入权。

是否能阻止旧执行者继续操作、设备是否支持所有权验证、控制通道如何隔离，都需要单独设计和验证。SA 的“重启能力”不自动解决这些问题。

<a id="future-control"></a>
## 13. 新 CA 与 SMA 的可视化流程方向

新 CA / Control Agent 是 Tauri 管理入口和独立 Rust 控制执行角色，CAF 是原 CA 冻结参考。新 CA 进入近期设计，不等于本轮批准设备实现。[U7]

```text
第三方 → 本系统 API 校验并持久化有效意图 → CA 原子领取
      → 固定意图和配置版本 → 映射/范围/现场条件 → 写暂存区并提交序号
      → PLC 校验与确认 → CA 核实结果 → 本系统执行回执
```

入库不自动具备执行资格；查询不等于领取。参数同步可以按源版本合并过时目标，动作请求逐条追踪。领取令牌/租约、唯一有效写入方、条件时间/质量及写前核实需定义，PLC 保有最终联锁。暂存/提交/确认节点封装多字段握手，需 PLC 程序配合。

API 接收、协议写成功、PLC 接受与设备完成分开记录；超时/断线/重启可能发生在动作之后，`unknown` 应先核实确认序号和现场结果。取消、租约失效和回退不能盲重试或撤销已发生动作；数据库去重不等于物理动作恰好一次。[U3]

### 13.1 共用代码，分别装配能力

推荐 Tauri + Vue 流程画布 + Rust Flow Core 解释版本化定义。SMA 负责事实加工和 API 投递，CA 负责持久意图与设备执行；共享编辑、校验、调度、分支和跟踪，各自拥有节点、权限、配置库、队列、状态和生命周期。SMA 在 Rust 装配/加载阶段拒绝设备写节点；重试工具不能统一决定副作用恢复。

Vue Flow 仅为候选。完整 Node-RED 为 Node.js 编排加 Rust 设备服务的备选，不能承诺任意导出 JSON/Function 节点由 Rust 直接执行。节点合同、有限 DAG/等待及典型流程详见[运行原理设计](AIIS_AW_Runtime_Design.md)。

### 13.2 CU 与两类可视化

CU 提供共享 UI 源码、布局主题、组件预览和可运行设计工作台。UI 编排描述页面呈现；SMA/CA 业务画布描述触发、数据转换、判断和动作。二者可以复用视觉组件，不能混用发布语义。

各 Agent 构建时引用 CU，安装运行无需 CU 工作台在线。Rust Flow Core 属于共享运行时能力，不归 CU 管理；CU 不直连 PLC，不持有执行状态。发布流程是安装规则，业务请求另行触发执行，预览无设备副作用。

### 13.3 DS：独立的设备模拟与联调工具

**DS / Device Simulator** 是 2026-10-18 增补的开发、测试与联调工具设计，不是生产 Agent，也不成为 DAA/SMA/CA 的生产前置。DAA 可向 DS 读取模拟值，CA 可向允许写入的模拟区下发数据；这些结果不证明真实 PLC 的行为、联锁或物理动作完成，也不复刻完整 PLC 执行系统。[U8]

管理 UI 可采用 Tauri 并复用 DAA/CU 适用页面和组件；采用类似 DAA 的 DB 新增、DB/UDT 导入和编辑管理逻辑，DB 号、名称、点位均可编辑，每个区域独立配置模拟模式和读写权限；本地 SQLite 保存配置属于设计方向。服务核心可评审 Python 或 Rust，语言、协议库及服务端读写能力尚未选定，不因 UI 技术而强制 Rust。

每个模拟实例独立拥有 ID、endpoint、内存、规则和日志，启动/停止/重置不影响其他实例。同机可通过不同端口区分 endpoint，前提是目标 S7 客户端/驱动支持自定义端口，不承诺所有客户端均支持。

| 可配置区域模式 | 设计行为 |
| --- | --- |
| 自动模拟区 | 按规则周期更新，默认客户端只读；内部规则写入与客户端写入权限分开 |
| 写入保持区 | 仅实例初始化或显式重置时应用初始值一次；此后允许的客户端写入保持，不被周期规则覆盖；重连不初始化 |

不固定 DB 编号、数量或必须两个 DB 的拓扑；自动模拟与写入保持是区域模式，不由 DB 编号决定。完整结构、地址范围及重叠校验仍须通过，运行中如何应用结构修改由后续实施合同确定。初始值与持续固定值策略分开；跨进程重启是否保存当前内存值待定。规则、客户端、UI 手改和重置都经统一实例内写入口，在改变内存前检查实例/地址/长度/类型/来源权限及重叠位冲突，处理并发；拒写须在入口返回失败，不能先成功再恢复旧值。

后续 Modbus 使用自身地址空间和寻址模型，不套用 S7 DB 编号；命令响应联动、状态机等响应模拟列为扩展，不在本轮实施。详细机制与未决项见[原理设计 DS 章节](AIIS_AW_Runtime_Design.md#ds)。

<a id="failure-behavior"></a>
## 14. 故障行为与可用性承诺边界

近期 API 断开时按有界缓冲和角色恢复策略降级；CA 已领取操作须核实结果，不能继续领取新工作。下表 AWB/PG/Redis/HA 行只在相应长期组件已实现后适用。

以下是未来验收目标，而非当前系统已经具备的能力。

| 场景 | 目标行为 | 不能夸大的部分 |
|---|---|---|
| AWC 关闭 | 已独立托管的运行程序继续运行 | 普通 sidecar 并不自动具备该保障 |
| AWB 不可用，Redis/PG 仍正常 | 已有配置下的采集、映射和授权归档可继续；SMA 按本地目标配置投递 | 中央配置更新、AWB 查询和未来任务领取不可用 |
| 中央 PG 不可用 | 本地 current/previous 仍可使用 | 发布、可靠中央任务和历史落库受影响 |
| AW Redis 不可用 | 按已实现且有界的缓冲策略降级 | 只有配置 SQLite 不等于能缓存采样数据 |
| PW 接口不通 | SMA 按容量和重试策略积压，采集不被平台无限阻塞 | 不承诺无限期或无限量缓冲 |
| HA 不可用 | 事件保留窗口内可恢复消费，积压可观测 | 超过流保留/存储容量仍可能丢失 |
| 新配置下载/校验失败 | current/previous 都不变 | 不提前覆盖 previous |
| 重复更新或回退请求 | 目标 revision 幂等确认 | 不执行盲目的二次交换 |
| 整个本地盘损坏 | 依赖备份/重新配置等恢复机制 | 同一 SQLite 双配置槽不是硬件容灾 |
| 数据过期但接口正常 | 返回明确时间、质量与过期信息 | 不用连接状态假装数据实时 |

本地配置可用、数据持续可采、历史可靠归档、平台可访问，是四种不同能力。不能用其中一项成立代替其他项的验证。

## 15. 从现有工程逐步演进的 Roadmap

### 15.1 当前阶段：工程基线与设计交付分开

ARCH-AW-001 保留原 CA 冻结参考、DAA/SMA 独立工程的证据；本次 ARCH-AW-002 修订角色和原理设计。仓库存在 console-ui 目录不证明 CU 能力完成；本轮不改变源码和历史 receipt。

不为三界额外创建强制顶层目录，不因白皮书收录建设 PG/Redis/AWB 或拆除 Projection。现行旧链路的切换、配置导入和新 CA 实施都另行限定范围。

### 15.2 候选能力路线

以下是依赖示意，不是版本、工期或已获批准 backlog。近期以本地配置和 API 为前提，不把中央发布安排成采集前置。

| 阶段 | 成果方向 | 后续验证关注 |
|---|---|---|
| E0 文档依据 | 修订本白皮书并形成详细原理设计 | 名称、阶段、合同草案与现状一致；独立文档 QA |
| E1 DAA 最小闭环 | S7 支持矩阵、本地 SQLite、DB/UDT 导入与受限推算、事实 API | 缺定义拒绝、TIA 偏移核对、编辑/启用隔离、批次与回执、旧配置迁移 |
| E2 有限共享底座 | CU 共享组件与工作台、SMA/CA 画布及 Rust Flow Core | UI 与流程边界、独立构建运行、节点权限、版本固定、无副作用预览 |
| E3 两类模拟闭环 | SMA 单目标投递；新 CA 持久意图到模拟设备握手 | 幂等与积压、原子领取、半写/丢回执/重启/unknown、资源仲裁 |
| E4 现场可靠性 | 授权设备接入、后台托管、容量与恢复 | PLC 联锁/实点、断网断电、长时间运行、唯一写入与回退；现场另批 |
| E5 按需中央化 | AWB/Axum、中央发布、PG/Redis、HA/SA、统一 AWC | 明确收益、迁移归属、配置权威切换和故障保障；非近期前置 |

先完成真实窄流程再提取公共能力；阶段可按依赖调整，不把所有 Agent 合并成一进程，也不提前制造空壳。

### 15.3 一开始固定目标边界，不是一开始实现全部组件

每次只交付明确完成的能力及其兼容范围。新增 DAA 就交付 DAA，不要求同一版本交付 SMA/HA/SA；但不能把尚未实现的职责先暗中塞进 DAA，等规模变大再拆。

当前已有耦合通过专项演进任务处理，不因为本稿出现独立角色，就追溯要求当前工程立即达到全部目标。只有目标角色正式进入实现，其新运行边界才作为该任务的验收要求。

### 15.4 实施触发条件

当真实项目需要独立设备生命周期、多平台复用、中央配置管理、可靠交付或历史归档时，可以选择对应能力进入实施。需要明确：改变什么、保留什么、涉及哪些配置/表/进程、如何验证、如何回退，以及谁批准。

不因“Rust 应该用上所有组件”“三界必须完整”或“目录看起来不够清晰”而创建工作。图中的组件名称不代替收益判断。

### 15.5 版本与现有路线

文档 v0.4 与仓库的 1.x/2.x 路线没有自动映射。程序、数据库 schema、配置 revision 和接口版本分别管理。

现有平台多后端路线仍由其自己的任务负责；如果后续确实产生冲突，再显式修订。主稿不安排 PW/AIW 开发阶段，也不把模型服务接入设为 DAA/SMA/HA 验收的前置条件。对应跨域背景另见 BG-09。

## 16. 渐进兼容与现场切换

### 16.1 素材复用不等于机械搬迁

既有设备适配、配置经验、Projection、TSS 和 Tauri 交互可作为演进材料。是否复用源码、抽取 crate 或重写适配，需要查看当时实现与合同，不能只凭名称认定兼容。[D3 §18]

原稿未读取 TSS 源码或重查 GitHub；本次只读核对本仓库现有文档、目录与 ARCH-AW-001 记录，未重新认证迁移，也没有构建或连接 PLC/数据库。

### 16.2 新旧链路要有明确的写入责任

试点或切换时，不能同时让旧 Projection 和 SMA 对同一业务字段各自自动写入而不处理冲突。对比验证可以观察两条链路，但正式结果必须有明确写入者。

设备连接也要评估负载，不能假定新 DAA 与旧采集器同时连接真实 PLC 没有影响。可在批准的范围使用录制数据、模拟器和受控只读验证，不将双跑当作默认无风险手段。

### 16.3 配置与运行数据分别迁移

TOML、SQLite 双槽、中央配置与新归档模型进入某个实际版本时，要明确现有 `.env`/YAML/数据库配置如何导入、验证和回退，不能仅靠改文件名完成迁移。

回退覆盖接口、写入归属、设备连接、数据/配置契约和 schema 兼容，不只是替换一个 executable。是否分仓和是否使用三界目录，不改变这些验收要求。

## 17. AW 范围内的验收与未决项

### 17.1 按实际实现能力选择验收

以下是后续目标清单，不要求当前版本同时通过全部项目。只对已获批准并实现的能力声明通过。

| 维度 | 需要证明的结果 |
|---|---|
| 工程连续性 | CAF 冻结参考及兼容路径有来源；新 CA 与采集角色不混称 |
| 新角色边界 | 各已引入角色独立启动、停止、诊断，不依附 AWC |
| 配置文件 | 同名 `agent.toml` 按角色解析；实例不串用配置或本地数据库 |
| 路径 | Tauri、终端、服务启动定位同一实例文件与数据 |
| 中央版本 | 不做五版本限制；在用及回退引用删除有服务端保护 |
| 本地双槽 | 下载失败不损伤双份；回退目标明确；重复请求不反向切换 |
| 状态隔离 | 配置切换不回退 outbox、消费进度、执行事实 |
| 采样语义 | 保留真实来源、采样时间和质量，不把处理时间冒充采样时间 |
| 数据输出 | latest、记录流与周期快照的保障范围明确 |
| AWB 接口 | 批量视图、授权、新鲜度、WS 快照/增量衔接和重连可验证 |
| SMA 投递 | 重复与乱序按契约处理；积压有界；平台故障不堵死采集 |
| HA | 原始通路独立；语义归档开关明确；JSON 载荷可解释 |
| 持久化 | 提交确认、重复消费、裁剪窗口与实际故障保障有证据 |
| 运行管理 | 无 UI 可运行；依赖故障不会导致无限重启 |
| 安全 | 管理用户、Agent、外部调用方身份分离；本地入口不绕过权限 |
| 迁移回退 | 新旧数据写入和设备连接归属清楚；配置及 schema 兼容可核查 |

未来 CA 的物理控制验收由控制专项另定，不把当前读取/映射闭环写成已具备安全控制能力。本稿也不对 PW 或 AIW 内部功能建立验收清单。

### 17.2 待实施决定，且仍限于 AW 的问题

| 议题 | 需要补充的内容 |
|---|---|
| 工程/部署组织 | 实际仓库和目录、OS/CPU、安装包、服务托管与账户；不预设三界顶层路径 |
| 配置合同 | 每类 `agent.toml` 的字段、覆盖优先级、校验、配置包与兼容规则 |
| 配置切换 | 内存与 SQLite 切换时机、崩溃恢复、停机升级和程序/schema 兼容 |
| 数据协议 | 原始/语义 schema、序列、时间、质量和无效数值表示 |
| 消息与缓存 | Redis Streams/MQTT 的具体职责、容量、持久化与裁剪 |
| 查询/投递 | 视图定义、HTTP/WS 消息、鉴权、确认、重试、积压和死信 |
| 归档 | JSONB 实体、分区、索引、批量参数、三个月含义、历史规则保留 |
| 离线与恢复 | 数据缓冲、容量耗尽行为、凭据保存、磁盘故障和重建 |
| CA 后续能力 | 执行接入、配置兼容、资源仲裁与现场失效行为 |

PW/AIW 的技术栈、模型、数据库和分析流程不再列为本稿“以后要做”的事项；它们作为独立背景资料供后续专项讨论。

本稿不承诺硬实时、零丢失、跨系统原子事务、无限缓冲、所有历史任意重放或自动控制主备。它们不是由 Rust、Redis 或 Agent 名称自动获得的性质。[D3 §19]

### 18.6 2026-10-15 内容修订结论

本次更新现行结论：CAF 与新 CA 分开；纳入 CU 共享源码/工作台；DAA 首版固定 S7 采集与本地 SQLite/API；SMA/CA 共用有限可视化与 Rust 底座；中央发布、PG/Redis、HA/SA 保留为长期方向。原稿以下 v0.4 来源结论作为历史保留，近期规则按本次阶段说明解释。

主稿回答“现有工业运行能力如何向 Automation World 演进”；背景资料保存“为什么这样分工、跨域还可以怎样协作”。两者相互引用，但都不把三界理念转成强制目录，也不自动启动当前仓库改造。
